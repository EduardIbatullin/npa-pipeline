# Справочник по API publication.pravo.gov.ru

Факты в этом документе получены эмпирическим тестированием (прямые запросы к живому API), не из официальной документации напрямую — официальная документация в ряде мест описывает параметры, которые на практике не работают. Дата последней проверки указана у каждого факта, где это важно.

Базовый адрес: `http://publication.pravo.gov.ru` (именно `http://`, не `https://` — при работе из некоторых окружений `https` зависает на уровне TCP-соединения; сам сервер по HTTPS может работать нормально, это ограничение конкретных клиентских окружений, не сервера).

Эндпоинты: `/api/Documents` (поиск/список), `/api/Document?eoNumber=X` (карточка документа, включает полный список органов-подписантов), `/api/SignatoryAuthorities`, `/api/DocumentTypes`, `/api/Categories`, `/api/PublicBlocks` (справочники), `/file/pdf?eoNumber=X` (скачивание PDF — не описан в официальной документации, найден эмпирически, работает).

## Параметры `/api/Documents` — что реально фильтрует на сервере

- `SignatoryAuthorityId` — фильтрует корректно. Для совместных документов (несколько подписавших органов) совпадает по **любому** из органов в списке подписантов, не только по основному (`isMain: true`).
- `Number` + `NumberSearchType` (`0`=точное совпадение, `1`=начинается с, `2`=заканчивается на, `3`=содержит) — все 4 режима проверены на реальных данных и работают корректно.
- `EoNumber` — работает и на списочном эндпоинте, не только в карточке документа.
- `JdRegNumber` — номер регистрации в Минюсте, точное совпадение, работает.
- `PageSize` — работает, но принимает только значения 10/30/100/200.
- `Index` — реальная рабочая пагинация (подтверждено: `currentPage`/`pagesTotalCount` корректны, страницы не пересекаются).

## Параметры, которые сервер полностью игнорирует (несмотря на то, что они есть в официальной документации)

- `DocumentDateFrom`/`DocumentDateTo`, `PublishDateFrom`/`PublishDateTo`, `JdRegDateFrom`/`JdRegDateTo`, `PeriodType`+`Date` — все варианты фильтрации по датам не работают, нужна клиентская фильтрация.
- `ComplexName` — не работает как текстовый поиск (документ описывает его как поиск по составному названию, включающему орган; на практике запрос с точным номером + `ComplexName` с посторонним текстом даёт тот же результат, что и без `ComplexName`).
- `DocumentTypeId` — не фильтрует на сервере (проверено прямым сравнением: правильный и заведомо неправильный GUID типа документа дают одинаковое число результатов при одном и том же органе). Тип документа нужно проверять на клиенте по полю `documentTypeId` в ответе.
- `SortDestination` — не влияет на порядок результатов.

## Формат номера документа (`Number`)

- Сервер сравнивает **точную строку**, без числовой нормализации: `"0402"` и `" 402"` НЕ совпадают с реальным номером `"402"` (0 результатов в обоих случаях).
- Регистр букв в номере (например, суффикс `ФЗ`/`фз`) **не влияет** на совпадение — сравнение регистронезависимое.
- Тип тире/дефиса **влияет**: типографское тире `–` (U+2013) вместо обычного ASCII-дефиса `-` в запросе даёт 0 результатов там, где документ реально существует с ASCII-дефисом.
- Проверено на выборке 2087 реальных номеров (два разных органа: Президент РФ, Минприроды) — ни одного номера с нетипичным тире/дефисом в самих данных на сервере не найдено. То есть проблема почти всегда на стороне запроса (если кто-то ввёл «неправильное» тире), а не на стороне данных сервера — но выборка не исчерпывающая (2087 из десятков тысяч документов в системе), поэтому нормализацию всё равно стоит делать с обеих сторон при сравнении на клиенте.

## Поиск по номеру без указания органа

`GET /api/Documents?Number=X&NumberSearchType=0` без параметра `SignatoryAuthorityId` работает и фильтрует по всей системе документов сразу (не только по одному органу). Проверено на двух номерах: `Number=402` → 672 результата (4 страницы по 200); `Number=1` (специально выбран как один из самых частых номеров, худший случай) → 3430 результатов (18 страниц). Даже в худшем случае это существенно дешевле переборного запроса по каждому из десятков-сотен кандидатов-органов по отдельности.

## Совпадения номеров (коллизии) — подтверждены на реальных данных, не гипотетические

- Один и тот же орган может использовать один и тот же номер повторно в разные годы: найден реальный пример (Минприроды России, тип документа «Приказ», номер `402`) — один документ подписан 19.07.2016 (`eoNumber = 0001201609130025`), другой — 20.07.2026 (`eoNumber = 0001202609240005`).
- Номера федеральных законов (`NNN-ФЗ`) повторяются **каждый год**, не являются сквозной глобально уникальной последовательностью, вопреки распространённому допущению: запрос «Президент РФ + номер `310-ФЗ`» вернул 10 результатов, по одному почти на каждый год с 2017 по 2026 (`eoNumber`: `0001201710300036` (2017), `0001201808030096` (2018), `0001201908020082` (2019), `0001202010010005` (2020), `0001202107020029` (2021), `0001202207140081` (2022), `0001202307100038` (2023), `0001202408080120` (2024), `0001202507310060` (2025), `0001202608040033` (2026)).
- Вывод: фильтрация по точной дате подписания на клиенте — обязательный шаг практически для любого поиска по органу+номеру, а не только защита от редкого краевого случая.

## Совместные (многосторонней подписи) документы

Документ с несколькими подписавшими органами находится через `SignatoryAuthorityId` **любого** из них с одинаковым `eoNumber`. Проверено на реальном примере: совместный приказ Минприроды России и Роснедра, номер `247/04`, `eoNumber = 0001202306010022` — найден одинаково что через GUID Минприроды, что через GUID Роснедра. Если поиск ведётся сразу по нескольким кандидатам-органам, такой документ будет найден несколько раз (по разу на каждого подписанта из списка кандидатов) — требуется дедупликация результатов по `eoNumber` перед тем, как считать результат неоднозначным.

## Первичный ключ документа — `eoNumber`

Каждый элемент ответа `/api/Documents` содержит поле `eoNumber` (например, `0001202609240005` = `0001` + дата публикации `20260924` + порядковый номер за день `0005`). Это внутренний идентификатор системы публикации, присваиваемый в момент размещения документа на портале, а не самим органом-издателем — дата в `eoNumber` это дата **публикации**, а не дата подписания документа (`documentDate`), они могут различаться. `eoNumber` невозможно вычислить заранее по реквизитам документа (орган, номер, дата подписания) — обратного поиска по этим данным в API нет; он становится известен либо как результат обычного поиска (уже есть в каждом найденном элементе), либо из внешней ссылки вида `http://publication.pravo.gov.ru/document/{eoNumber}`. Если `eoNumber` уже известен — это самый быстрый и однозначный способ получить документ: `/api/Document?eoNumber=X` (карточка) или `/file/pdf?eoNumber=X` (сам файл).

## Граница охвата по времени

Подтверждено на реальных данных (переход сразу на последнюю страницу результатов для Президента РФ, 19198 документов / 96 страниц): самые старые документы в системе имеют дату подписания 07–08.11.2011, дату публикации 10.11.2011. Это совпадает с официально заявленной датой запуска портала. Документы, подписанные раньше этой границы, в системе отсутствуют в принципе — нужен другой источник. Важно: граница определяется датой **публикации** на портале, а не датой подписания документа — документ, подписанный до 08.11.2011, но опубликованный позже этой даты (например, с задержкой), в системе может быть. Поэтому нельзя заранее (до попытки поиска) отсекать запрос по дате подписания — сначала всегда нужно выполнить поиск, и только при отсутствии результата и дате подписания раньше границы возвращать явный статус «вне охвата системы», а не путать его с «документ не найден».

Отдельное от системной границы явление: у конкретного органа самая ранняя запись в системе может быть значительно позже 2011 года (например, у Минприроды России самая старая запись в выборке — начало 2015 года) — это не сигнал о другой системной границе, а особенность того, когда конкретный орган начал публиковаться под своим нынешним идентификатором (переименование, реорганизация и т.п.).

## Прочие технические ограничения

- Формат документа на сервере — всегда PDF, других форматов (DOCX/RTF) нет.
- Крупные PDF (30+ МБ) могут обрезаться при коротком таймауте скачивания — нужен таймаут 120–180 секунд и проверка целостности после скачивания.
- При быстрых последовательных запросах без пауз наблюдались единичные обрывы соединения на транспортном уровне (~10% в выборке из 30 запросов подряд) — не подтверждённый целенаправленный троттлинг, но нужен retry с backoff в HTTP-клиенте.
- `documentDate`/`publishDateShort` — проверено на выборке 400 реальных документов, время во всех случаях `T00:00:00`, аномалий часового пояса не найдено (но выборка ограничена, не 100% гарантия для всех документов в системе).
