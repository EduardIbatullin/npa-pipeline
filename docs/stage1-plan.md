# Этап 1 — скачивание НПА через API publication.pravo.gov.ru

Черновик плана, прошёл два раунда предметного разбора (алгоритм и контракт результата проверялись на реальных запросах к API, не только логически). Продолжает уточняться — не финальная версия.

## Цель

Программа (без ИИ в рантайме), которая по известным реквизитам документа находит и скачивает его официальный PDF с `publication.pravo.gov.ru`, с точностью нахождения нужного файла, близкой к 100% (при условии что документ на сервере есть).

## Режимы работы (согласовано: пока только 1 и 2, массовый сбор отложен)

Режимы 1 и 2 — не два разных алгоритма, а один и тот же процесс с разным результатом резолвинга органа (см. «Резолвинг» ниже): резолвер всегда возвращает набор кандидатов-GUID размером 0, 1 или много. Разделение на «режимы» сохранено только как термины для входных данных пользователя, дальше по коду — одна схема.

- **Режим 1** — на входе известен орган (название или сразу GUID) + номер + дата подписания. Если дан GUID напрямую — резолвинг тривиален (набор из 1 кандидата). Если дано название — резолвинг должен дать **ровно один** кандидат, иначе обрабатывается так же, как режим 2 (см. ниже), а не как отдельная ошибка.
- **Режим 2** — на входе неполное/родовое название органа (например «Министерство финансов» без региона) + номер + дата; резолвинг даёт много кандидатов или (после нормализации названия) не даёт ни одного.
- **Режим 3 (отложен)** — массовый/пакетный сбор документов по критериям (диапазон дат, категория и т.п.) — не в скоупе этапа 1 сейчас.

## Алгоритм поиска (детали параметров API — [`docs/api-reference.md`](api-reference.md))

1. Если известен `EoNumber` — использовать его напрямую (`/api/Document?eoNumber=X`, `/file/pdf?eoNumber=X`). Самый быстрый и однозначный путь, но обычно неизвестен заранее.
2. **Резолвинг органа** (см. раздел «Резолвинг» ниже) даёт набор кандидатов-GUID: 0 (орган не распознан), 1 (однозначно) или много (родовое название).
3. **Нормализация номера перед запросом и перед любым сравнением на клиенте**: привести все виды тире/дефиса (`–`, `—` и т.п.) к ASCII `-`, убрать пробелы и символ `№`. Регистр в запросе можно не трогать (сервер сравнивает регистронезависимо) — но **клиентское** сравнение нормализованных номеров всегда без учёта регистра. Нормализация применяется **к обеим сторонам**: и к номеру из запроса, и к полю `number` из ответа сервера, сравнение — уже после нормализации обеих строк, а не только запроса (проверено на выборке 2087 реальных номеров: тире с ошибкой в самих данных сервера не встречено, но клиентское сравнение всё равно делаем по нормализованным строкам как дешёвую защиту от необнаруженных случаев).
4. Основной запрос — если кандидат один: `GET /api/Documents?SignatoryAuthorityId=<GUID>&Number=<номер>&NumberSearchType=0&PageSize=200`, с проходом по всем страницам через `Index`, если `itemsTotalCount` больше одной страницы (не просто брать первую страницу — иначе часть результатов теряется молча).
5. Основной запрос — если кандидатов много (или резолвинг дал 0, но пользователь всё равно указал текстовое название — этот случай явно обрабатывается на шаге 11): один запрос `GET /api/Documents?Number=<номер>&NumberSearchType=0&PageSize=200` **без** `SignatoryAuthorityId` (подтверждено: фильтрует по номеру системно, по всем органам сразу), с проходом по всем страницам. Затем на клиенте: (а) отфильтровать по точной дате (см. п. 6), (б) сузить по совпадению `signatoryAuthorityId` с одним из кандидатов. Веерный перебор запросов по каждому кандидату-GUID отдельно — теоретический запасной путь на случай неприемлемого объёма без органа; порога, когда объём считать «неприемлемым», не определено, и на проверенных реальных числах (худший случай — номер `"1"`, 3430 результатов/18 страниц) он не понадобился ни разу. В коде этапа 1, скорее всего, не реализуется — фиксируется здесь как идея на будущее, а не как задача.
6. **Обязательный шаг**: клиентская фильтрация по точной дате (`documentDate`) — сервер не фильтрует по дате, а коллизии (тот же орган + тот же номер, разные годы) подтверждены как не редкость: например, номер федерального закона `310-ФЗ` повторяется **каждый год** (проверено 2017–2026) у Президента РФ — то есть фильтрация по дате обязательна практически всегда, не только в редких коллизиях.
7. **Дедупликация по `eoNumber` перед оценкой неоднозначности** — обязательна при поиске по нескольким кандидатам (и в веерном переборе, и при сужении по кандидатам после запроса без `SignatoryAuthorityId`). Подтверждено на реальном совместном приказе: документ с несколькими подписантами находится через GUID **каждого** из них с одинаковым `eoNumber`. Без дедупликации совместный документ ошибочно считается «неоднозначным».
8. **Запасной поиск по цифровой части номера** запускается, если результат **после шагов 4–7** (запрос + фильтрация по дате + дедупликация + сужение по кандидатам) — 0, а не если сырой ответ сервера на точный запрос был 0. (Иначе типичный провал: пользователь ввёл `310`, нужен `310-ФЗ`; точный запрос `310` находит непустой, но не тот результат — не совпадающий с датой/органом — и без этого условия запасной поиск вообще не запустится.) Правила:
   - Цифровая часть номера — то, что стоит до первого нецифрового символа. Если номер не начинается с цифры (`П-123`, `ММВ-7-3/123@`) — цифровая часть пустая, запасной поиск **не выполняется**.
   - Запрос `NumberSearchType=1` (starts) по цифровой части. На клиенте — обязательная проверка границы: совпадением считается только номер, где сразу после цифровой части идёт нецифровой символ или конец строки (проверено на реальных данных: без этого правила поиск `310` находит также `3100-...`, `3101-...` и т.п. — цифровая граница не проверяется сервером).
   - Если резолвинг дал одного кандидата — запасной запрос **включает** `SignatoryAuthorityId`, объём тогда неважен (ограничен одним органом).
   - Если кандидатов много или 0 (но название всё же дано) — запасной запрос идёт без `SignatoryAuthorityId`, но **только если цифровая часть не короче 3 символов**. Проверено на реальных данных: `NumberSearchType=1` без органа даёт для `"1"` — 413409 результатов/2068 страниц, для `"31"` — 22584/113, для `"310"` — 1673/9 (уже приемлемо). При более короткой цифровой части без единственного кандидата запасной поиск не выполняется — результат остаётся тем, что дали шаги 4–7.
   - Результаты запасного поиска проходят те же шаги 6–7 и 10 (фильтрация по дате, дедупликация, порог неоднозначности) — отдельное правило «один или несколько вариантов суффикса» не нужно, шаг 10 уже разруливает это через `ambiguous`. Единственное отличие: результат, найденный только через запасной поиск (не через точное совпадение), помечается в контракте результата полем `match_type: digits_only` (вместо `exact`) — вызывающая сторона видит более слабое совпадение, и такие случаи можно отдельно считать в измерении точности (эталонный набор).
9. 0 результатов после шагов 4–8 (в том числе если запасной поиск не выполнялся — пустая цифровая часть или короче 3 символов без единственного кандидата) → `not_found`, если дата подписания не раньше границы охвата системы (см. `docs/api-reference.md`), иначе `out_of_range`. **Важно**: эта проверка выполняется только после неудачного поиска, а не до — граница охвата определяется датой публикации на портале, а не датой подписания, и документ, подписанный до границы, но опубликованный позже, в системе может быть.
10. >1 результата после дедупликации по `eoNumber` и фильтрации по дате → `ambiguous`, возвращать список кандидатов, не выбирать автоматически.
11. **Диагностика перед финальным `not_found`** — обязательна в двух случаях, оба приводят к `not_found` с диагностическим полем (контракт результата фиксирует именно этот статус, без альтернативы):
    - **Резолвинг дал 0 кандидатов**, но название всё же было дано — запрос и так шёл без `SignatoryAuthorityId` (шаг 5), диагностика получается бесплатно: всё, что нашлось после фильтрации по дате (но ни с чем не сопоставлено, раз кандидатов не было), и есть диагностическое поле.
    - **Резолвинг дал ровно одного кандидата, но итог всё равно `not_found`** — свободных данных нет (запрос шёл со `SignatoryAuthorityId`, сужен на сервере), поэтому перед возвратом `not_found` выполняется **один дополнительный запрос без `SignatoryAuthorityId`** по тому же номеру+дате исключительно для диагностики (возможно, орган резолвлен неверно — переименован/устарел). При **нескольких** кандидатах этот дополнительный запрос не нужен — запрос и так шёл без `SignatoryAuthorityId` (шаг 5), диагностика уже получена бесплатно, как и в случае «0 кандидатов» выше.
12. Тип документа (`DocumentTypeId`) не фильтрует на сервере — сверять на клиенте по полю `documentTypeId` из ответа, если тип документа известен и важен для проверки.

## Резолвинг органа (единый для режимов 1 и 2)

- Хардкодить список GUID органов нецелесообразно — на сервере 103 федеральных + 3846 региональных органов.
- Архитектура: локальный кэш/база, построенная разовым (периодически обновляемым) обходом `PublicBlocks` → `Categories` → `SignatoryAuthorities`.
- Полнотекстового поиска по названию на сервере нет (`ComplexName`/`Name`-параметры ненадёжны для этой цели) — резолвинг названия в кандидатов делается по локальному кэшу, а не через API поиск.
- Нормализация названия при сопоставлении с кэшем нужна отдельно от нормализации номера: ё/е, регистр, кавычки, распространённые сокращения («Минфин» → «Министерство финансов»). Пока не проработано — открытый пункт дизайна.
- Органы переименовываются и упраздняются (реорганизация регионального министерства и т.п.) — нужно решить, хранит ли кэш старые GUID при переименовании (иначе поиск по историческому названию сломается) и как часто кэш обновлять. Пока не проработано — открытый пункт дизайна.
- Результат резолвинга — всегда набор кандидатов (0/1/много), который дальше обрабатывается по единой схеме шагов 2–11 алгоритма выше, без отдельной ветки «режим 1 vs режим 2» в коде.

## Контракт результата

Фиксированный набор статусов на выходе:
- `found` — однозначный результат; содержит поле `match_type: exact | digits_only` — `exact`, если совпадение получено на точном запросе номера (шаг 4/5), `digits_only`, если только через запасной поиск по цифровой части (шаг 8). Различие важно вызывающей стороне и для измерения точности на эталонном наборе (ложные `found` по неполному номеру считаются отдельно от точных).
- `not_found` — среди резолвленных кандидатов органа ничего не найдено. Если по тому же номеру+дате найдены документы **других** органов (не входивших в резолвленных кандидатов) — они перечислены в диагностическом поле (шаг 11: список органов и `eoNumber`), это сигнал, что резолвинг органа мог промахнуться (переименование, нераспознанное название), а не то, что документа нет вовсе. Если диагностическое поле пустое — документа действительно нет нигде в системе.
- `ambiguous` — несколько результатов после дедупликации по `eoNumber` и фильтрации по дате; возвращать список кандидатов для явного выбора, не выбирать автоматически.
- `out_of_range` — искомая дата подписания раньше границы охвата системы (см. `docs/api-reference.md`), определяется **только после** неудачного поиска, никогда заранее.
- `invalid_input` — входные данные некорректны до всякого обращения к серверу: нет номера, дата не парсится, и т.п. Не путать с `not_found` — это разные причины отказа.
- `network_error` / `integrity_error` — сбой на сетевом уровне или при проверке скачанного файла. Если к моменту сбоя `eoNumber` уже был найден (поиск прошёл успешно, упало именно скачивание/проверка) — этот `eoNumber` обязательно возвращается вместе с ошибкой, чтобы повторная попытка могла сразу пойти по короткому пути (шаг 1 алгоритма — прямой запрос по `eoNumber`), не повторяя поиск заново.

## Метаданные, сохраняемые рядом с PDF

При каждом скачивании — `eoNumber`, исходный запрос (как он был передан), найденные реквизиты (орган, номер, дата, тип), URL, sha256, размер файла, дата скачивания. Назначение: пригодится этапам 2–3, и позволяет не скачивать повторно документ с уже известным `eoNumber`.

## Проверка целостности PDF после скачивания

Конкретные шаги: сравнить полученный размер с заголовком `Content-Length` ответа; проверить сигнатуру `%PDF` в начале файла и маркер `%%EOF` в конце; дополнительно открыть файл PDF-библиотекой (например `pypdf`) и прочитать число страниц, чтобы убедиться, что файл не оборван и не битый.

## Как измерять «близко к 100%»

Нужен эталонный набор реальных документов с заранее известным `eoNumber` (предложение: 50–100 штук), включающий заведомо сложные случаи. Часть уже найдена эмпирически и может быть использована как готовые примеры (полные детали и методика — [`docs/api-reference.md`](api-reference.md)):
- документ с подтверждённой коллизией — Приказ Минприроды России №402: `eoNumber = 0001201609130025` (подписан 19.07.2016) и `eoNumber = 0001202609240005` (подписан 20.07.2026), один орган, один номер, разные годы;
- номер, повторяющийся ежегодно у одного органа — Федеральный закон №310-ФЗ, Президент РФ, один пример на каждый год 2017–2026 (`eoNumber`: `0001201710300036`, `0001201808030096`, `0001201908020082`, `0001202010010005`, `0001202107020029`, `0001202207140081`, `0001202307100038`, `0001202408080120`, `0001202507310060`, `0001202608040033`);
- совместный (многосторонней подписи) документ — Приказ Минприроды России и Роснедра №247/04, `eoNumber = 0001202306010022`, должен находиться одинаково через GUID любого из двух органов;
- номер с буквами/дефисом (`NNN-ФЗ`, `NNN-п` и т.п.);
- крупный PDF (30+ МБ);
- документ до границы охвата системы (ожидаем `out_of_range`, граница — 07–08.11.2011, см. `docs/api-reference.md`).

Считать отдельно долю верных ответов и долю ложных `found` — ложное «найдено» опаснее, чем «не найдено».

## Известные технические ограничения

Полный список проверенных эмпирически фактов о поведении API (формат PDF, граница охвата 07-08.11.2011, устойчивость к частым запросам, формат дат) — в [`docs/api-reference.md`](api-reference.md), чтобы не дублировать и не расходиться с текстом при обновлении.

Отдельно: инструмент обращается к серверу по `http://`, не `https://` — осознанное решение (в части клиентских окружений `https` к этому хосту зависает на уровне TCP, при том что сам публичный документ не секретен). Целостность скачанного файла защищается контрольной суммой (`sha256` в метаданных), а не транспортным шифрованием.

- Приёмка в нормативную базу и карта влияния (этап 3).
